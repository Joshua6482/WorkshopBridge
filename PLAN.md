## Open Work

- **Orphaned sub-mods:** DONE. `JobManager.removeStaleSubMods` removes the leftover folder only when its `mod.info` ID matches the removed ID and no other map entry claims that ID; otherwise the folder is left untouched.
- **Mod dependencies:** DONE Oct 2026, pending in-game verification. Steam's Web API has no dependency field (verified live: `GetPublishedFileDetails` + `includechildren=true` returns no children for mods; children are collections-only. `IPublishedFileService/GetDetails` needs a publisher key, and `GetQueryUGCChildren` is the client-side Steamworks API, so neither is usable). Instead Java scrapes the public workshop page's `Required items` panel (`WorkshopDependencies`: transitive, cycle-safe, depth-capped, best-effort so Steam hiccups never block installs). `wbCheckDependencies` starts a background "deps" job; the job status carries a `deps` list of {id, title, installed}. After a fresh download or adopt, Lua shows a "Required Workshop items" dialog (Install all via the normal import job path, or Skip). Per-item choosing is a possible follow-up.
- **Server-join mod download prompt:** DONE Oct 2026, pending in-game verification. Researched from the decompile (`ConnectToServerState`, `ConnectionDetails`): in non-Steam mode the game skips its workshop states entirely (TestTCP → CheckMods), so a missing mod fails the join with `OnConnectFailed` carrying `"... [ModID: x, WorkshopID: y]"` (first missing mod only) and then disconnects — no prompt, no resume; the flow is download → manual rejoin. The decompiled `ConnectToServerState` item-update path was investigated and is not suitable. Implementation: Lua `WB_ServerJoin` hooks `OnConnectFailed`, parses the `[ModID/WorkshopID]` suffix, and calls new `wbGetServerMods`, which re-reads the server's FULL mod list from the failed join's `connectionDetails` packet (`ServerJoinMods`: synchronous on the game thread while `ConnectToServerState.instance` is still set; deterministic forward parse of the Start/TestTCP sections; the optional workshop section disambiguated via the `10745/9412/0` start-location magic ints; any mismatch yields null and Lua falls back to the single mod from the message). A dialog on the `ConnectToServer` screen lists every missing mod — downloadable ones via **Download all** (one `wbImportMods` force-install job, then `wbInvalidateModCaches` so the rejoin sees them), manual-install ones (no workshop ID, e.g. transitive `mod.info` `require=` deps) dimmed. Silent in Steam mode (vanilla workshop flow owns it). Deliberately no workshop "required items" lookup here: the server already enumerates what it needs, and scraping a page per server mod would hammer Steam on big mod lists. In-game test: join a modded server without its mods, expect the dialog listing all missing mods, Download all, then rejoin successfully.
- **posix_spawn troubleshooting:** Expand `docs/INSTALL.md` with Windows launcher guidance and Linux instructions for distinguishing the steam-run sandbox case from native launch failures.
- **Internationalization:** Move Lua-facing labels, status text, dialogs, and error flashes into `WB_Strings.lua`; move Java messages such as `Net.friendlyMessage` and hints into a strings class or `.properties` bundle. Mod names are not currently parsed or displayed by this code; Java NIO handles Unicode paths, and the JSON parser handles `\\u` escapes including surrogate pairs.
- **Jar signing script:** done (`./sign.sh`, repo root). ZBS is ZombieBuddy's own Ed25519 scheme (see zed-0xff/ZombieBuddy `doc/ModSigning.md`). One-time: Ed25519 keypair auto-generated into `~/.signing/` (private key never in the repo), SteamID64 asked once and saved next to the key (machine-local, not in the repo; joshua needs a Steam account for the identity even as a GOG player); later runs are fully automatic. Public key published as `JavaModZBS:<64 hex>` on the Steam profile or via PR to ZombieBuddy's `authors/` (keeps the profile private; keys there are authoritative). The documented `zb-gradle-plugin` does not exist (absent from the ZombieBuddy repo and the Gradle Plugin Portal), so the script implements the format directly with openssl: SHA-256 the release jar, sign the canonical payload `ZBS:<SteamID64>:<JAR_SHA256>`, write the `WorkshopBridge.jar.zbs` sidecar next to the jar. Regenerate on every rebuild; ship the `.zbs` alongside the jar in the release zip. Round-trip tested on a dummy jar (openssl verify passes, fails on a tampered jar); the sidecar format was additionally parsed by ZombieBuddy itself in-game (verification got as far as the Steam key lookup, which failed only because the public key is not published yet). Signing proves identity + integrity and enables ZombieBuddy's trust-author auto-approval, not safety.
- **Release script:** done (`./release.sh`, repo root). Interactive: prompts for the version (default today's date as `YYYY.MM.DD`, overridable via `--version=`/`WB_VERSION`), warns when the working tree is dirty, then compiles with diagnostics off, ZBS-signs the fresh jar, stages the mod folder (`42/`, `common/`, `poster.png`, plus `java-src/` with only `src/`, `build.gradle`, `README.md`: the official ZombieBuddy sample mod ships its Java project inside the mod folder, and the game ignores the extra directory; `java-src/libs/` is excluded because it holds compile-only dependency jars including possibly the proprietary `projectzomboid.jar`, which must not be redistributed), stamps `modversion=<version>` into the staged `mod.info` (the repo file is left untouched), and zips to `dist/WorkshopBridge-<version>.zip` (gitignored). Prints the zip and jar SHA-256 hashes, a VirusTotal report link for the zip (`https://www.virustotal.com/gui/file/<zip sha256>`; the link points at the zip because that is the file users download and VT links are keyed by file hash, and it shows a report once the zip has been uploaded there at least once), and a ready-to-paste release notes file; offers to create the GitHub release via `gh`. When `VT_API_KEY` (free VirusTotal API key) is set, the zip is submitted to VirusTotal automatically via the v3 `POST /files` endpoint. Flags: `--yes` (non-interactive), `--no-build` (package the tree as-is). End-to-end tested with `--no-build` on a dummy jar: zip layout, modversion stamping, hashes, VT link, and notes file all verified.
